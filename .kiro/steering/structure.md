## Architecture Layers

La arquitectura sigue un flujo unidireccional de dependencias:
Route Handler / Server Component ↓ Service Layer ← business logic, orchestration ↓ Repository Layer ← data access (Prisma only) ↓ Database (PostgreSQL)
**Regla estricta:** cada capa solo puede importar de la capa inmediatamente inferior. Un Route Handler nunca importa de un Repository directamente.

## Naming Conventions

| Elemento | Convención | Ejemplo |
|---|---|---|
| Componentes React | PascalCase | `PetCard.tsx`, `AdoptionForm.tsx` |
| Hooks personalizados | camelCase con prefijo `use` | `useAuth.ts`, `usePets.ts` |
| Servicios | camelCase con sufijo `.service` | `pet.service.ts` |
| Repositorios | camelCase con sufijo `.repository` | `pet.repository.ts` |
| Schemas Zod | camelCase con sufijo `.schema` | `pet.schema.ts` |
| Tipos TypeScript | PascalCase, sufijo `Type` o `Props` | `PetType`, `PetCardProps` |
| Variables y funciones | camelCase | `getPetById`, `isLoading` |
| Constantes globales | SCREAMING_SNAKE_CASE | `MAX_UPLOAD_SIZE_MB` |
| Rutas de API | kebab-case | `/api/adoption-requests` |
| Directorios | kebab-case | `adoption-requests/`, `pet-form/` |

## Component Guidelines

- **Server Component por defecto.** Agregar `"use client"` solo cuando se necesite interactividad, hooks de estado o acceso al DOM.
- **Un componente por archivo.** No exportar múltiples componentes del mismo archivo (excepto subcomponentes muy pequeños y estrechamente acoplados).
- **Props tipadas siempre.** Definir una interfaz `XxxProps` en el mismo archivo o importar desde `types/`.
- **No lógica de negocio en componentes.** Los componentes solo presentan datos y dispatching de eventos. La lógica va en hooks o servicios.
- **Collocated tests.** El test de `PetCard.tsx` vive como `PetCard.test.tsx` en el mismo directorio.

## API Route Handler Pattern
ts // src/app/api/pets/route.ts import { NextRequest, NextResponse } from "next/server"; import { z } from "zod"; import { createPet } from "@/services/pet.service"; import { createPetSchema } from "@/schemas/pet.schema"; import { getCurrentUser } from "@/lib/cognito"; import { ApiResponse } from "@/types/api.types"; export async function POST(req: NextRequest) { try { const user = await getCurrentUser(req); if (!user) { return NextResponse.json<ApiResponse<null>>( { data: null, error: { code: "UNAUTHORIZED", message: "Authentication required" } }, { status: 401 } ); } const body = await req.json(); const parsed = createPetSchema.safeParse(body); if (!parsed.success) { return NextResponse.json<ApiResponse<null>>( { data: null, error: { code: "VALIDATION_ERROR", message: parsed.error.message } }, { status: 400 } ); } const pet = await createPet(parsed.data, user.id); return NextResponse.json<ApiResponse<typeof pet>>({ data: pet, error: null }, { status: 201 }); } catch (error) { console.error("[POST /api/pets]", error); return NextResponse.json<ApiResponse<null>>( { data: null, error: { code: "INTERNAL_ERROR", message: "Unexpected error" } }, { status: 500 } ); } }

## Import Alias

Usar siempre `@/` para imports absolutos desde `src/`. Nunca usar rutas relativas que suban más de un nivel (`../../`).
ts // ✅ Correcto import { PetCard } from "@/components/pets/PetCard"; import { petService } from "@/services/pet.service"; // ❌ Incorrecto import { PetCard } from "../../../components/pets/PetCard";

## File Creation Checklist

Antes de crear un nuevo archivo, verificar:
1. ¿Pertenece a la capa correcta? (component vs service vs repository vs lib)
2. ¿El nombre sigue las convenciones de la tabla anterior?
3. ¿Tiene sus tipos definidos en `types/` o inline si son locales?
4. ¿Si es un Route Handler, valida input con Zod y usa el envelope de respuesta estándar?
5. ¿Si es un componente, es Server Component por defecto?
